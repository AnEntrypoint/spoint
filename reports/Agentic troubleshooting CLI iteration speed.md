# Stop losing cycles before adding parallel workers

The fastest wins for spoint's agentic troubleshooting runs are not raw parallelism; they are removing the lost cycles. The local gate (`scripts/check.mjs` `main()`) stops at the first pre-witness failure, so a stale bake or stale SDK typing costs a full gate cycle per fix, and a failing witness prints only six lines with no saved log. On the CI side, the 38-witness pool already overlaps, but the fire gate runs 10 witnesses serially for 147 s, and about 66 s of serial work is serialized only because of an over-broad regex. Every saving below is estimated from code structure or from recorded durations, not timed end to end, because no gate run was timed in the notes. On the gm side, the agent's own waits are the biggest measurable loss: `sleep` is a fixed 15 s poll, the `crawl` budget discards completed steps on a kill, and a stale gm-mcp bundle was serving every verb in the sampled run. ([spoint_local_loop](/workspace/spoint/research_notes/Agentic%20troubleshooting%20CLI%20iteration%20speed/spoint_local_loop.md)) ([spoint_agent_tooling](/workspace/spoint/research_notes/Agentic%20troubleshooting%20CLI%20iteration%20speed/spoint_agent_tooling.md))

## Fail-fast gates and lost failure output cost the most local cycles

`scripts/check.mjs` `main()` calls `process.exit(1)` in roughly a dozen static-gate branches (relative imports, cache keys, TSL imports, apps manifest, SDK typings, app imports) before the witness arm starts. A stale heightfield pin is the common case: `scripts/check-cache-keys.mjs` fails, the gate exits, and the developer finds the next red only after re-running. The fix is to collect static-gate failures into the same report and still run the witness arm, so one run shows every failure. The same file's `runNoGpuWitnesses` keeps only six echo lines (`NO_GPU_WITNESS_ECHO_LINES`) and a `maxBuffer` of 16 MB, and a child that exceeds the buffer is reported as "exited 1" because `e.code` is undefined. The local note estimates this fail-fast change as the largest single loss per stale-bake incident, and it is low risk. ([spoint_local_loop](/workspace/spoint/research_notes/Agentic%20troubleshooting%20CLI%20iteration%20speed/spoint_local_loop.md)) Pair it with writing each witness's full stdout and stderr to `.gm/witness-out/` and printing that path on failure, since the directory already exists and holds the progression-witness outputs now in this checkout. Add a detector for `ERR_CHILD_PROCESS_STDIO_MAXBUFFER` so a buffer overflow stops reading as a witness fault. A `must` miss should print the actual RESULT line, not only the regex.

A second local lever is selection. `scripts/check-cache-keys.mjs` already contains an import walker (`importClosure`), and the note measured that 74 of 91 gate witnesses have closures of 50 files or fewer. A proposed `scripts/check-affected.mjs` would select witnesses whose closure, plus literal paths they read, intersects `git diff --name-only`, while always running the structural gates. For a leaf edit this drops roughly 70 to 80 percent of witnesses; for `src/apps/AppRuntime.js` it saves almost nothing, because 14 witnesses import the app runtime. The local note warns that a direct `node scripts/<file>.mjs` run skips each entry's `must` regex (`check.mjs`, `must` check), so the affected runner must apply each entry's `must` and `args`, or a local PASS can still fail the gate. ([spoint_local_loop](/workspace/spoint/research_notes/Agentic%20troubleshooting%20CLI%20iteration%20speed/spoint_local_loop.md))

## Bake re-runs and browser cold starts are the hidden waits

Changing any file in `BAKE_INPUTS_HEIGHTFIELD_BAKE` (`src/static/BakeCodeVersion.js`) changes `HEIGHTFIELD_BAKE_CODE_VERSION`, and `check-cache-keys.mjs` then fails every shipped `.hf` until `scripts/bake-heightfield.mjs` is re-run. The breadth is real: the declared list equals the 28-file closure of the bake, and `presetInputs()` pulls every `src/presets/*.js`, so an edit to `rts.js` forces a tps re-bake that never reads it. The notes found the bake CPU-only for hashVersion 2 (`bakeFromCpuSampler`), so it needs no browser lease and can overlap the witness arm. The safe lever is a per-world input list derived from the closure rather than hand-written, which keeps the closure check passing. A content-based staleness digest is faster still but can miss a change if the sample set is sparse, so it needs the carve and seed points. ([spoint_local_loop](/workspace/spoint/research_notes/Agentic%20troubleshooting%20CLI%20iteration%20speed/spoint_local_loop.md))

Browser witnesses are a different kind of waste. `scripts/lib/cdp-browser.mjs` `launch` starts a fresh Chrome with a fresh profile for each of the 53 witnesses that import it, and `scripts/lib/browser-lease.mjs` `release` kills the browser tree and deletes the profile for every holder. Parallelism is not available because the GPU is one adapter, but the cold start is. The proposal keeps Chrome alive for the next holder with the same fingerprint, records `port` and `browserPid` in `owner.json`, and opens a fresh target per witness, with a TTL so a crashed holder cannot pin the browser. The cross-witness state leak risk is real, so each witness needs its own browser context. The notes also found that a second agent's lease wait is never logged, so `browser-lease.mjs` `acquire` should record `waited_ms` and queue position before any of this is tuned. ([spoint_local_loop](/workspace/spoint/research_notes/Agentic%20troubleshooting%20CLI%20iteration%20speed/spoint_local_loop.md)) ([spoint_agent_tooling](/workspace/spoint/research_notes/Agentic%20troubleshooting%20CLI%20iteration%20speed/spoint_agent_tooling.md))

## CI wall time is the witness pool and the fire gate, not the pages build

The CI `check` job ran 522 to 561 s across two runs. Per the note, the static gates take about 10 s, the 38 pooled witnesses 184 s of work, the 55 serial witnesses 339 s, and the fire gate 147 s, which `check.mjs` runs after the witness phase. The biggest near-term saving is `scripts/fire-witness-gate.mjs` `main()`: its `for (const name of WITNESSES)` loop runs tps-game (69.9 s), peer-rollback (40.6 s) and eight smaller witnesses serially, so concurrency would bring that to about 70 s, a saving of about 75 s, provided each witness binds no fixed port and every failure is still reported. Only four of the ten were checked for literal ports. ([spoint_ci](/workspace/spoint/research_notes/Agentic%20troubleshooting%20CLI%20iteration%20speed/spoint_ci.md))

The classifier is the other lever. In `scripts/check.mjs`, the `FIXED_RESOURCE` regex misfiles six witnesses whose ports are randomised (`tps-game-player-movement-witness.mjs`, `capture-server-witness.mjs`, `transport-churn-witness.mjs`, `relocation-ground-wait-witness.mjs`, `tps-game-spawn-ground-hold-witness.mjs`), about 54 s of serial work, and the `TIMED_MEASUREMENT` regex matches the bare label `MEASURED`, which serialises four witnesses that read no clock (`prediction-wedge-witness.mjs`, `grass-rim-draw-ring-witness.mjs`, `sky-aerial-perspective-count-witness.mjs`, `hmr-rebuild-count-witness.mjs`), about 66 s of serial time. Before reclassifying, check the two browser-driven ones for CDP ThreadTime reads, because a browser witness measures browser-side CPU. Sharding the witness phase across three matrix jobs through a `SPOINT_CHECK_SHARD=i/n` filter in `check.mjs` `plan` is estimated at about five minutes saved per push, but that figure is arithmetic on serial-equivalent work, not a measured wall, and the static gates would need to run once. The notes also flag that the Pages docs page silently drops three of four sibling repos in CI (`scripts/generate-docs-site.js`), which is a correctness fix rather than a timing one. ([spoint_ci](/workspace/spoint/research_notes/Agentic%20troubleshooting%20CLI%20iteration%20speed/spoint_ci.md))

## The agent's own waits and gm verbs dominate the agentic loop

Inside a gm walk, the largest measured waste is the agent's own waiting, not the gate. The `sleep` gm verb took 15.0 s on each of 39 calls because its poll is fixed, so a two-second wait costs fifteen; replacing it with a `wait_ms` body is a no-risk change. The `crawl` verb's helper budget (`CDP_HELPER_BUDGET`, 100 s in `crawl.rs`) gave a p50 of 71 s per call, and one of eight calls was killed at that budget and returned `steps: []`, discarding every step it had finished. The notes did not find the 90 s figure as a constant, so the budget should be exposed per call and the partial steps kept. Console capture is attached only when the same call has a console op, so an empty `messages: []` cannot be told from silence; the note proposes returning `capture_attached` on every call. The `codesearch` literal mode returned zero for a multi-word query with the hint "no line matched as ONE phrase", which reads as a finding, so a zero should report `unproven_zero` first. These verbs live in `/workspace/gm`, not in this repo, and the notes trace them to `crawl.rs` and `crawl_cdp_tools.mjs`. ([spoint_agent_tooling](/workspace/spoint/research_notes/Agentic%20troubleshooting%20CLI%20iteration%20speed/spoint_agent_tooling.md))

The gm verb tail is also a queue problem. `phase-status` has a p50 of 14 ms across 113 dispatches but a 138.7 s maximum, and one runner update held a dispatch for 99.6 s according to `.status.json`, so updates should move to idle time. Verbs repeat within a session: `phase-status` ran six times on one fingerprint, `git_status` three times, `prd-list` 21 times across 14 sessions. Caching `phase-status` by HEAD sha plus the `prd.yml` mtime, `git_status` by HEAD plus a worktree stat digest, and `ci-status` by commit sha (a finished run never changes) removes most of that repetition. The `gm-mcp` process was also serving bundle 0.2.128 while 0.2.129 was installed, so every verb in the sample ran on the older bundle; the relaunch must happen between walks. ([spoint_agent_tooling](/workspace/spoint/research_notes/Agentic%20troubleshooting%20CLI%20iteration%20speed/spoint_agent_tooling.md))

## Caveats and what to measure first

The notes are candid that nothing here is timed end to end. The gate was not run, the bake's wall time was not measured, the lease wait was never recorded, and the CI sharding figure ignores CPU contention on shared runners. The local checkout (`ba8850a`) also trails `origin/main` (`b90df90`), so the CI line citations were read from origin and may not match local files; the local-loop note's line numbers have already drifted by one or two lines, so cite symbols, not line numbers. The first step for every change is to record per-witness seconds, which `check.mjs` already prints on success and never persists, and to log lease wait. Those two records would turn the estimates above into measured savings and set the witness pool order from past runs.

## Conclusion

The shortest path to a faster spoint troubleshooting run is to stop losing cycles, not to add workers. Keeping the gate going past a stale pin, writing full witness output to `.gm/witness-out/`, and making a `sleep` or `crawl` body honest about its budget remove whole re-runs, which are the costliest event in the sampled data. Parallelism comes second: fire-gate concurrency and the witness shard are worth roughly five minutes per push together, but only after the regex misclassifications are fixed, since the classifier currently decides what runs in parallel. The notes' open question is the one that decides the rest: the 90 s crawl cap was never found in code, and until the lease wait and per-witness durations are logged, every saving stays an estimate.
