# Collapse live-game diagnosis into fewer launches and reads

Most of the wallclock in a spoint engine, server or graphics debugging run is spent on round trips rather than on the game itself: a fresh headful Chrome per question, a crawl reply that loses its steps on a kill, a server that prints nothing about its own boot, and a gm-mcp that is still serving an older bundle. The four research notes ground about twenty ranked changes, and the cheapest of them need no runtime change at all: restart gm-mcp, fix the `count`/`messages` mismatch in `consoleReport`, enable `Log` in `cdp-browser.mjs`, and record swallowed shader compile errors in `warmupShaders`. None of these savings has been timed end to end, so every figure below is an estimate unless it is marked as read from code or re-checked this session. The largest single unknown is the cold path: the only recorded cold-load number is 54552 ms, and the 77369 ms and 85692 ms boot figures and the 110 s and 150 s shader figures from the brief are not in the repo. A cheap boot-timing instrument would settle that. This report extends the earlier `reports/Agentic troubleshooting CLI iteration speed.md`, which covers the local gate, CI sharding and the agent's own wait loops; it does not repeat those findings.

## The live-game CLI is the first place to cut round trips

The crawl verb (implemented in `/workspace/gm`, not in this repo, so its paths are the notes' citations and were not re-opened here) gives an agent one browser per call, and that is where most of the waste sits. Console capture is armed only when the same body contains a `console` line, so a message emitted in an earlier call on the same `session=` is lost. The notes record that `consoleReport` in `crawl_cdp_tools.mjs` computes `count` eagerly at the `console` line (around lines 483-485) while passing the live array as `messages`, so a `console` line placed before the actions can report `count: 0` beside a non-empty array. **[code-read]** The fix is to compute `count` from the final array, which costs nothing and carries no risk; the saving is one diagnostic re-run per console question, **[estimate]** about one crawl call, roughly 30 to 70 s by the notes' p50 of 71 s per call. The same function would take a `console [where text~<s>] [limit=N]` form reusing `eventMatches`, which removes the need to hand-write an `events Runtime.consoleAPICalled where args.0.value~[terrain]` recipe. The recipe itself is usable today, but only for string or number first arguments; object arguments need `args.0.description`. **[code-read]**

The `steps: []` loss is the other crawl problem. The helper budget is `CDP_HELPER_BUDGET = 100 s` in `crawl.rs`, the helper watchdog fires at budget minus 10 s, and a hard kill discards the JSON that the helper only prints at the end (`crawl_cdp.mjs` around lines 254 and 265). The notes' mechanism is that the watchdog `cleanup()` awaits `Runtime.evaluate` with no deadline, so a page in a busy JavaScript loop never lets the watchdog write. **[code-read, cause unverified]** Two changes address it: write the partial `out` to a file after each step and have `crawl.rs` (around lines 909-913) read it when `run.result` is `None`, and wrap `currentUrl` in `cleanup()` (`crawl_cdp.mjs` around line 168) with the existing `withDeadline` helper in `crawl_cdp_tools.mjs`. The first is about one small write per step and removes a whole lost crawl per kill; **[estimate]** the lost crawl was one of eight calls in the sample. The reply also omits `steps` and `tab` in `verbs.md` (lines 593-603), and `press_uid` is in the grammar but absent from the step table at `verbs.md:631`; both are documentation-only corrections.

Screenshots should default to `.jpg`. The screenshot code already supports it (`crawl_cdp_tools.mjs` around lines 656-661), and the reply returns a path, so the agent reads bytes only when it needs them. **[code-read]** The saving is in image tokens per check, **[estimate]** not measured.

The browser start itself is the next wait. Each `launch()` in `scripts/lib/cdp-browser.mjs` spawns a fresh Chrome with a fresh profile, and about 68 `chromium.launch` call sites under `scripts/` do the same. The notes propose a named-lease reuse mode that keeps the browser alive and opens a fresh target per witness, but module-level state in `BrowserServer.js` (`_lastTodSync`, `_deliveredWorldFingerprints`) leaks across loads, and the adapter pin is per launch. **[code-read]** This is high risk and the saving is **[estimate]** one launch per avoided witness. It should wait until the combined probe below proves that most questions can be answered without a second launch.

## Server boot and internals are silent to the CLI

`ServerBoot.js` contains no `Date.now`, `performance.now` or `hrtime` call, so no phase duration is ever printed. **[code-read]** Adding one `[boot-timing] <phase> <ms>` line after each `await` at `ServerBoot.js` lines 153, 158, 167, 190, 192, 198, 214, 225 and 231 is the cheapest change in this report: it costs one log line per phase, has no behaviour change, and is the only way to replace the unverified 77 s and 86 s figures with a measurement. The live server already exposes a loopback probe, `GET /debug/server` routed through `ServerAPI.js` line 142 to `handleDebugServer` in `ServerAPIRoutes.js` lines 95-109, which returns tick, players, entities, connection stats and heap, so a boot probe can curl it after `[server] ... TPS` appears; the timing fields would join that JSON. The tick loop itself has no per-tick or lag log, and `[tick-dilation]` at `src/sdk/server.js` line 194 is the only tick line. **[code-read]**

Several server boot steps look serial when they may not need to be. `prewarmFiles` (`ServerBoot.js` line 214) and the environment `ensureProgressive` `Promise.all` (line 225) are independent and both block `listen`, so joining them is a candidate saving of the shorter of the two. `physics.init()` in `src/sdk/server.js` line 42 does not depend on `locateWorld` or `loadWorldModule`, so starting it earlier could overlap it with manifest loading. The second `waitForPendingTrimeshBuilds()` at `ServerBoot.js` lines 197-200 follows one already made in `ServerAPI.loadWorld` line 114, so it is normally near zero. **[code-read, dependencies unverified]** Each is an **[estimate]** of a few hundred milliseconds to a few seconds on the cold path, and none has been timed. The singleplayer `WorkerEntry.js` `init()` does not await `setupTerrainStreaming` (around line 113), so the heightfield can arrive after `init()` returns; that is a correctness question for the spawn-hold path before it is a speed one.

The spawn-hold release is silent on success. `holdSpawnUntilGrounded` in `src/sdk/Relocation.js` (lines 167-195) logs on hold and on timeout, but a successful release places the player and logs nothing; the only signal is the `player_teleport` broadcast in `placePlayerAt` (line 212). **[code-read]** `terrainFieldMissingAt` (lines 153-157) returns `false` when the streamer is null or lacks `coversPosition`, which reads as "covered" and sends the hold to the ray probe. This is the silent-default class that `AGENTS.md` forbids, and the fix is to return a reason code, as the researchers propose. A coverage census over `HeightfieldStreamer.groundlessCenters()` (`src/terrain/HeightfieldStreamer.js` lines 271-277) would show which rings are built, but it needs a live server and is not node-only.

## Graphics state needs one probe, not three launches

The notes found that a graphics diagnosis today needs three or four separate reads, each in its own witness and browser: `window.__rendererInfo` (set at `client/app.js` line 255), `window.__lastShaderWarmup` (`client/core/SceneSetup.js` lines 378-389), `window.__qualityGovernorState` (`client/core/RenderControls.js` lines 49-50), and `window.__overdrawProbe.counters()` (`client/core/RenderControls.js` lines 96-99). **[code-read]** All four are already present, so a single `scripts/` probe built on `probeGpu` and `assertGpu` in `scripts/lib/gpu-probe.mjs` (lines 13-94) could read them in one `page.evaluate` on one launch. This is the highest-value graphics change: **[estimate]** two or three launches saved per diagnosis, with no runtime change and low risk, provided the probe asserts `installed === true` on each global so an absent counter does not read as a measured zero.

The invisible shader failures are worth instrumenting before anyone reads a frame. `warmupShaders` in `client/core/SceneSetup.js` at line 411 wraps `renderer.compileAsync` and falls back to `renderer.compile` inside two empty catches, so a shader that fails to compile is discarded and shows up only as a missing draw later. **[code-read]** Pushing `{url, message}` into a list and including it in `_record` costs about five lines and adds one field to an existing record; the saving is every future "why is this not drawn" run that would otherwise start from a live pipeline. Similarly, `installStuckPipelineRecovery` (lines 243-265) counts nothing until three `RenderPipeline|CommandBuffer` errors land within two seconds; incrementing a counter on every matching `onError` at line 251 makes a single failure visible. **[code-read]** Because `renderer.onError` is asynchronous, a probe must yield one `MessageChannel` turn before reading that counter. Whether `device.onuncapturederror` fires in a headful CDP session is **not verified**; the AGENTS.md statement is taken as given.

Counters that are read but never incremented make a silent pass, and `perf-run.mjs --require-count` (line 65) already guards the default list. Adding `compileFailures` and a pipeline-error count to that list is one line, but **[estimate]** a previously passing run may now fail, so the counter must be incremented in a smoke run first. The `flagNumber` helper in `scripts/lib/witness-args.mjs` may turn a bare `--flag` into the boolean `true`, which `Number()` reads as 1; **[unverified]** the researchers did not confirm the helper's behaviour, so that is an investigation, not a change.

## Terrain and bake iteration

The bake pin is the largest recurring rebuild in this area. `HEIGHTFIELD_BAKE_CODE_VERSION` in `src/static/BakeCodeVersion.js` hashes the full text of every entry in `BAKE_INPUTS_HEIGHTFIELD_BAKE` (lines 82-108), and `presetInputs()` (lines 49-54) pulls every `src/presets/*.js`, so an edit to one preset re-pins and re-bakes the tps-game heightfield. **[code-read]** Narrowing the glob to the world being baked saves a full re-bake per unrelated preset edit; the risk is that `scripts/check-cache-keys.mjs` lines 114-124 fail when an imported file is missing from a declared list, so the per-world list must be derived from the import closure, not written by hand. The **[estimate]** saving is one bake-and-recheck cycle per preset edit, which the notes did not time.

`ProgressiveBake.js` has a worse, quieter cost for the same reason: its key hashes the full text of `BAKE_INPUTS_PROGRESSIVE_BAKE` including comments, so a comment-only edit to any of those files misses every progressive bake. **[code-read]** That collides with INVARIANT 3, because the comment sweep will edit exactly those files. Hashing a comment-stripped form, or pinning the version by hand, avoids the mass miss. Separately, `getProgressive` (`ProgressiveBake.js` lines 144-146) rereads the whole GLB with `readFileSync` on every call through `_hashFile`; memoizing by path, size and mtime is a small change with **[estimate]** unmeasured savings per asset load.

The bake log times only the sampling loop: `scripts/bake-heightfield.mjs` line 84 prints `N*N samples in Date.now()-t0`, where 66049 is 257 squared, and the 435 ms figure is that sampling step. **[code-read]** The codec and the `check-cache-keys` run are untimed, so the full re-bake wall clock is unknown. Timing those two stages next to line 84 is a one-line-per-stage change.

The terrain key may be too narrow. `terrainBakeSlice` in `src/shared/terrainConfig.js` (lines 112-114) includes `seed`, `radius`, `reliefScale`, `anchorDir`, `hashVersion` and `carves`, and omits `extent`, `center` and `res`. **[code-read]** `bakedTerrainMismatch` in `src/terrain/LatticeSurface.js` returns null when keys match, so a bake with a changed extent or centre and the same key passes the check. This is a correctness risk rather than a speed item, and its severity depends on a check the notes did not find; it needs a witness before anyone relies on the key alone. Adding a content-digest check that reads only the `.hf` headers would fail in under a second, since `check-cache-keys.mjs` already decodes each header (lines 129-138) and computes the pin from source without running the bake.

## gm tooling friction, measured in this session's own replies

Every codesearch reply this session carried `bundle_stale: true` and a `stale_tree` block with `behind: 31`, and the `gm` replies run to several kilobytes, mostly repeated bundle and tree metadata. **[re-checked]** The notes measured replies of 12 to 15 KB. Moving those blocks to a `notices` field returned only when they change would cut tokens on every verb, and that is the single cheapest gm change. The notes also record that a multi-word literal codesearch returns a zero with the hint `no line matched`, and that such a zero reads as a finding; **[re-checked]** this session's `Log.enable` zero used a single term, and its `hint` correctly described the match as exact-substring. A `unproven_zero` status when the query has spaces would stop the misreading.

The `sleep` verb's fixed 15 s poll is the largest measured waste in the agent loop. The agent-tooling note records a 15.0 s duration on each of 39 calls, so a two-second wait costs fifteen; a `wait_ms` body is a no-risk change in `/workspace/gm`. **[recorded durations, not re-run]** The `phase-status` verb has a p50 of 14 ms and a 138.7 s maximum, and one runner update held a dispatch for 99.6 s; moving updates to idle time and caching `phase-status` by HEAD sha plus `prd.yml` mtime, `git_status` by HEAD plus a worktree stat digest, and `ci-status` by commit sha removes most repeats, which the notes counted as six, three and 21 per session. **[recorded counts]**

## Not measured, and the single run that would settle each question

Nothing in these notes was timed end to end. The cold path is the largest gap: one headful cold load with the `[boot-timing]` lines in place, plus `performance.getEntriesByName('boot:world-exists')` (`client/app.js` line 382) and `loadingMachine.isReady`, would give the first real figure for the 77 s and 86 s claims and locate the largest serial step, which is `createTerrainBackdrop` at `app.js` line 613 and was never read. Whether the crawl steps loss is a busy-loop artefact is one crawl against a page that runs `while(true){}` after a click, with the partial-file change in place, which either returns the earlier steps or does not. The Log capture change is settled by one witness that calls `page.on('Log.entryAdded', ...)` and logs a deprecation warning. The lease wait and per-witness durations, which `scripts/check.mjs` prints on success but never persists, would settle the witness ordering in the earlier report, and one timed `scripts/check.mjs` run would settle the local gate figures. The bake timing is settled by one re-bake with the codec and check stages timed. The shader-error instruments are settled by a deliberately broken shader in a headful run, which should show a non-empty `compileFailures` field.

## Conclusion

The cheapest path to a faster engine loop is to stop paying for a second browser and a second crawl for each question, and to make the server and the shader pipeline report their own time and failures. Seven of the twenty ranked items are changes of one to five lines, and four of those, the console count fix, the `Log` subscription, the compile-failure record and the boot timings, produce information that today must be guessed. The named-lease browser reuse and the bake-input narrowing are larger changes whose savings depend on those instruments landing first.

The notes also show that the measurement debt is now the bottleneck. The only verified cold figure is 54.5 s, the widely quoted boot and shader numbers are not in the repo, and the crawl loss has an unverified cause. Until the boot timings and one headful cold run exist, every saving in this report stays an estimate, and the first action after the gm restart should be to produce that run.
