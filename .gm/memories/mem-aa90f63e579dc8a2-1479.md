Two frame-time instruments in scripts/perf-run.mjs disagree by ~2x and both are reported in the JSON, so any before/after comparison must name which one. (1) The in-page rig (window.__rig) is one requestAnimationFrame loop and pushes dt = now - lastNow between rAF timestamps: that is the true frame cadence. On arm D-metric-v2 (bundle 5133a3d0d11c036d, head 6733daf5, idle gpu3d=4) it reads p50 7.04 ms, p95 13.96, p99 20.89, avg 10.82, max 833 -- i.e. 142 fps at the median on a 144 Hz panel, with 2 and 3 vsync misses at p95/p99. (2) window.__perf.exportSession() comes from client/core/FrameMetrics.js, fed by client/app.js:2576 `_perf.sample(performance.now() - now)` where `now` is the rAF timestamp argument, so it measures vsync-timestamp to end-of-JS-work and INCLUDES callback dispatch latency; it read p50 13.45, p95 19.47, p99 23.92 on the same 3371 samples. The app's own adaptive DPR/VDRS and the PRD row's 'CPU 13.6 ms' figure come from this second instrument (_perf.lastMs), so that number is not CPU work per frame and not the frame interval -- it is work plus dispatch latency, and it runs about 2x the true interval. Also: exportSession() reports `duration: samples/60`, a hardcoded 60 fps assumption, so its duration field is meaningless (56.2 for a 35 s window). And startup.refreshHz is window.__vsync's rolling median read at overlay-reveal time, which is the cadence DURING the world build (47.99 Hz on D-metric-v2), not the display refresh rate (144 Hz).
