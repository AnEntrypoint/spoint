client/app.js _finishLoading cannot be gated on the planet (window.__terrain) instead of the whole _buildWorldScenery, because the PLAYABLE_BUDGET_MS=4000 prewarm is what populates the world before the player gets control. Vegetation/Rocks/Grass prewarm (client/core/Vegetation.js:507, Rocks.js:273, Grass.js:381) front-loads the same loadChunk work the per-frame path does, but streamRing only spends LOAD_BUDGET_MS=2 per frame (Vegetation.js:448,463), so 4000ms of prewarm spread over frames is ~33s at 60fps. Skipping it in the wait means the player spawns in a playable radius that is empty and fills in over ~33s.

The retry decision is already planet-gated: the adopt/rebuild branch is `if (!window.__terrain && _terrainCfg)` (client/app.js:348) and the toast is the same test at :366, so the SCENERY_BUILD_TIMEOUT_MS cap bounds only how long we wait, not what we decide. The planet landing 12.8s before the build settles means the cap firing inside 17ms of build-settle costs 17ms of prewarm, not a spurious retry.

Measured on SwiftShader (scripts/page-boot-witness.mjs --gl=swiftshader, uncontended): backdrop returned 28489, foliage-started 28491, rocks+grass created 28556, boot:scenery-built 44039, boot:vegetation-created NEVER fired - so vegetation creation itself is the long pole and can exceed the cap by minutes on a software renderer. Any planet-gated reveal therefore ships a world with no trees at all there.

The spawn hold is not at risk from an earlier reveal: holdSpawnUntilGrounded (src/sdk/Relocation.js:71) has exactly one caller, _spawnJoiningPlayer (src/sdk/ServerHandlers.js:81); it runs server-side at join and gates release on the heightfield via terrainFieldMissingAt/coversPosition (maxMs SPAWN_HOLD_MAX_MS=20000), independent of when the client calls _revealWorld(). Caveat: terrainFieldMissingAt returns false when ctx._terrainStreamer is missing, so no hold at all in that case.
