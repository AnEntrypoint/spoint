The Tier-0 baselines (PF-nv-720, 720b, 720c, PF-amdreal-720; memos project/tier0-cpu-gpu-profile-2026-10-05 and project/tier0-full-tables-and-sample-size-2026-10-05) were taken with the host CPU at 87-100 percent: 16 cores pegged by about 8 litebox_runner_linux_on_windows_userland processes of another project (about 0.9 core each), planet-multiplayer-harness children, peer-profile-harness and agent processes, with the GPU idle near 8 percent waiting on the host. Therefore absolute wall-clock numbers from those arms (frame ms, fps, long tasks, overlay reveal, boot marks, script ms) are contaminated by CPU contention and must not be compared as absolute values; per-function SHARES of the CPU profile are usable because contention scales all main-thread work roughly together; GPU timestamp-query times are largely contention-insensitive. From 2026-10-05 16:15 every arm records main-thread CPU time per frame (Performance.getMetrics ThreadTime delta / frames) as the primary CPU metric and host CPU samples (all-core load and top 5 processes in cores, before / every 10 s / after); an arm whose host CPU reaches 90 percent is flagged contentionSensitive. Hang evidence for N2-nv-1 (15:35-15:43, raw src/ worker because the prebuilt worker was stale): the world built (overlay hidden at 38.5 s, player connected and on ground) and the page then stopped answering CDP for over 5 min; host CPU was 100 percent with the coarse heightfield taking 18458 ms instead of 22 ms and module evaluation 16290 ms instead of 1350 ms, so the hang is most consistent with host starvation; a worker error was not observed.
