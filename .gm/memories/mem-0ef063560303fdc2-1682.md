project/node-process-exit-races-uv-async-send-2026-10-06: `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), file src\win\async.c, line 76` on Node v24.15.0 (bundled libuv 1.51.0) is the `assert(!(handle->flags & UV_HANDLE_CLOSING))` inside `uv_async_send()` -- a SEND to an already-closing uv_async_t, not a double uv_close. Do not hunt for a duplicated close call; hunt for who exits while handles are still in flight. spoint creates no uv_async handle at all: `process.report.getReport().libuv` shows `async=3` identically in a bare `node -e` and at every stage of a 3-cluster-world run, so all three are Node internals (V8 platform flush-tasks async, WorkerThreadsTaskRunner async, threadpool wq_async). The abort fires AFTER the last application output is flushed (proved by merging stdout+stderr: the RESULT JSON is complete, the assertion is the final line), i.e. at the final `process.exit(0)`, never during teardown. At that instant `libuv` shows tcp=6 (2 http servers + 4 sockets) still mid-close; the closes were started but never awaited. Fix proven: poll `process._getActiveHandles().length` until 0 before finishing -- it drains in ~62 ms and tcp goes 6 -> 0, then the process ends naturally with exit 0; only fall back to `process.exit(0)` when something is still referenced (scripts/cluster-world-harness.mjs `quiesceLoop`). A Jolt-free script that closes 2 servers + 4 sockets and exits does NOT reproduce (0/320 runs), so this needs real in-flight V8/background work and is a rare race: 3 aborts in ~20 unfixed runs, 0 in the fixed arm. Consequence for every headless harness: never end with a bare `process.exit(0)` after starting teardown; await the drain.
