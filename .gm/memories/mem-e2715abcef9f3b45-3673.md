## Resolved mutable: webgpu-planet-canvas-color-not-persisted-across-threejs-render

Real root cause found (not the autoClear/loadOp/MSAA-canvas-resolve hypothesis, which was disproven live: renderer.currentSamples measured 0 at runtime, not 4). Live-inspected node_modules/three@0.185.1/src/renderers/common/Renderer.js: renderer.needsFrameBufferTarget is true (tone mapping + sRGB output color space active, confirmed live: toneMapping=4, outputColorSpace='srgb'), so THREE's scene render targets an internal offscreen RenderTarget (Renderer.js:1425 _getFrameBufferTarget(), a real RGBA16F MSAA(4x) target, confirmed live via renderer._getFrameBufferTarget()+renderer.backend.get(...).msaaTexture), never the canvas directly. After the scene pass, Renderer.js:1813 _renderOutput() draws a fullscreen opaque 'Output Color Transform' NodeMaterial quad from that offscreen target into the canvas -- this quad pass unconditionally covers every canvas pixel every frame regardless of autoClear (the comment at Renderer.js:1864 confirms autoClear is force-overridden for this specific pass), so whatever planet-orchestrator-webgpu.js previously wrote directly into renderer.backend.context.getCurrentTexture() was always discarded by this quad, independent of the client/core/RenderGraph.nodes.js autoClear=false guard (which only ever affected THREE's OWN scene pass, never this output stage). Fixed in packages/mapspinner/src/webgpu/planet-orchestrator-webgpu.js by adding resolveThreeOwnedColorTarget(renderer, colorFormat): when renderer.needsFrameBufferTarget, obtain the real GPU resource via renderer._getFrameBufferTarget() + renderer.backend.get(fbTarget.texture) and draw into its .msaaTexture (matching format+sampleCount) instead of the canvas, so mapspinner's terrain/sky/water become part of the SAME buffer THREE's own scene draws (loadOp='load', autoClear=false) into and later resolves+tonemaps to canvas; falls back to the canvas MSAA companion (backend.textureUtils.getColorBuffer()) or the raw canvas texture when no framebuffer target exists. pipeline-cache.js's getPipeline() gained sampleCount support (multisample descriptor + cache-key dimension); vdrs-composite.js's BilinearUpscale/Fsr1Upscale RCAS pass gained per-call sampleCount+colorFormat pipeline variants (mirroring DepthWriteback's existing lazy-pipeline pattern) since the framebuffer target's format (rgba16float) differs from the canvas's (bgra8unorm/preferred format). Live-verified via gm browser verb against http://localhost:8099/?singleplayer&world=tps-game&webgpu=1, REAL full game loop (never a manual planet.frame() call): patched GPUQueue.prototype.submit to copyTextureToBuffer-readback an NxN grid of renderer.backend.context.getCurrentTexture() on every real submit, grouped by GPUTexture object identity to isolate per-frame submit sequences. Across 9 independently-sampled real animation frames (post-cleanup confirmation batch: texId 118/119/120, each 3 submits/frame; earlier confirmation batch: texId 175-180, 6 frames, 8x8=64-point grid), the FIRST submit of every frame shows 100% black samples (canvas untouched pre-THREE, confirming mapspinner no longer writes there directly) and the LAST submit of every frame (after THREE's scene pass + output/tonemap quad) shows 0% black samples with real varied terrain/sky/water/scene colors (e.g. [116,115,61],[40,79,48],[82,109,132]) -- reproduced identically across all sampled frames, zero flakiness. Prior to the fix, the same grouped-by-frame methodology on the original code showed the opposite pattern (first submit already non-black from mapspinner's direct canvas write, last submit 58% black, i.e. the reported bug).
