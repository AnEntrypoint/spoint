On this shared box, ms/tick deltas below about 40% are NOT admissible evidence -- decide CPU optimizations on counted work units instead. Measured 2026-10-06 with scripts/cpu-skip-witness.mjs (real tps-game server, 4 real PhysicsNetworkClients, 120 buttons / 120 destructibles / 120 dynamic props), using a control arm whose expected delta is zero: before-vs-before on the SAME build moved integer counters < 1%, but after-vs-after on the same build moved _lastCollisionMs +36.6% (0.310 -> 0.423 ms/tick) and _lastInteractMs +26%. So a timer delta under ~40% on this machine is host contention, not a result. The rows that were landed were therefore decided on counted integer work units with a byte-parity or staleness correctness check alongside: entity-bin double-buffer took new bin buffers/tick from 79.41 to 0.58 with 0 byte mismatches over 150k comparisons and a decode-memo hit ratio of 1.0011 (gate: within 1%); getSnapshot transform caching took _encodeEntity calls/tick from 371.51 to 105.94 against 105.94 entities measured changed per tick in the same run (gate: changed+1) with 0 stale of 150,626 snapshot-vs-live position checks; collision grid re-buckets/tick 120 -> 0.00; interactables distance tests/tick 480 -> 0.00. Where a timer moved but fell under the floor (e.g. _lastCollisionMs 0.233 -> 0.310) it was reported as UNMEASURED, not as a win. Also load-sensitive: the byte-identical fraction of the entity bin was 0.378 before, 0.254 at 64 ticks/s and 0.109 at 52 ticks/s as the shared box starved the tick loop. Corollary: pin every reuse cache to the code that produces it (a code-version marker), otherwise a cache silently serves stale results -- and a BAKE_INPUTS_* list that contains its own pin file is self-referential and can never match.
