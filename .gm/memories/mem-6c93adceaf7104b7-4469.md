## Resolved mutable: webgpu-e2e-global-dither-hatch-corruption-and-broken-sky-atmosphere

Investigated whether the permanent MeshBasicNodeMaterial_433 pipeline failure (sibling mutable webgpu-e2e-meshbasicnodematerial-433-dxc-permanent-fail, resolved this session) is the root cause of the spreading dither/hatch corruption + broken sky. CONFIRMED PLAUSIBLE MECHANISM, same failure class independently found in a SECOND location: packages/mapspinner/src/webgpu/pipeline-cache.js (this session's own new file, used by sky-render.js/vdrs-composite.js/terrain WGSL passes) had the IDENTICAL anti-pattern as three.js's own Pipelines.js -- MapspinnerPipelineCache.getPipeline() called this.device.createRenderPipeline(descriptor) and cached the result in this._pipelines UNCONDITIONALLY with ZERO error-scope check, meaning a transient/rare WGSL compile failure in mapspinner's OWN sky/terrain/HPF pipelines would silently wedge that pipeline forever with not even a console error (weaker than three's own partial handling). Since sky-render.js was independently verified correct in ISOLATION earlier this session but fails under the FULL game context, and the ground/sky/HUD/minimap corruption only appears and WORSENS over the ~130s sustained session (not present in start/mid screenshots), a silently-wedged mapspinner pipeline triggered mid-session by the same class of rare compile race is a coherent, source-grounded explanation independent of (and additive to) cross-contamination from THREE's own MeshBasicNodeMaterial_433 failure. FIXED: packages/mapspinner/src/webgpu/pipeline-cache.js getPipeline() now wraps device.createRenderPipeline() in device.pushErrorScope('validation')/popErrorScope().then(), evicting the cache entry (this._pipelines.delete(cacheKey)) and console.error-logging on failure so a future getPipeline() call for the same state/shader retries fresh instead of reusing a silently-broken handle forever. LIVE-VERIFIED with a REAL (non-mocked) GPU validation failure in the actual browser against the real Dawn/D3D12 device (gm browser verb, http://localhost:8099/?webgpu=1): imported the live pipeline-cache.js module, instantiated MapspinnerPipelineCache against window.__app.renderer.backend.device, called getPipeline() with deliberately malformed WGSL ('BROKEN NOT WGSL @@@') -- console shows the real Dawn WGSL parser error ('Error while parsing WGSL: :1:1 error: unexpected token') followed by our new 'mapspinner pipeline-cache: createRenderPipeline failed (fullscreen-blit): [Invalid ShaderModule...] is invalid due to a previous error' log; result confirmed stillCachedAfterFail:false, sizeAfterFail:0 (broken entry correctly evicted), then a subsequent getPipeline() call with valid WGSL succeeded cleanly (goodPipelineCreated:true, goodCached:true, finalSize:1) -- proving the fix both recovers from a real failure and does not regress normal operation. Cross-poisoning via shared GPU resources (bind-group-layout cache, shared color/depth render targets) remains the plausible link for why THREE's separate MeshBasicNodeMaterial_433 failure could also visually manifest as sky/ground/HUD corruption -- per AGENTS.md's own recorded architecture (webgpu-planet-depth-target-mismatch-under-framebuffer-target, webgpu-planet-water-vdrs-not-wired) mapspinner's sky/VDRS compositing explicitly reads/writes shared depth and color render targets with THREE's own scene; if THREE's main-scene pass (containing the 91 wedged MeshBasicMaterial instances) fails to complete cleanly every frame from tick 124 onward, downstream passes compositing against that pass's now-stale/partially-written shared textures would show exactly the observed flat-band sky and accumulating dither/hatch pattern. This is the SAME class of bug (uncaught pipeline failure -> permanently poisoned cached GPU state, no retry) found and fixed in two independent locations (three.js's own Pipelines.js, addressed via the stuck-pipeline-recovery mitigation in the sibling mutable; and mapspinner's own pipeline-cache.js, addressed directly here) rather than a single provably-shared trigger, since the underlying DXC/WGSL compile race could not be forced to reproduce on demand this session (consistent with prior sessions) to directly single-step tick 124 and confirm which specific pipeline(s) were involved in the sky corruption. Both fixes are complementary defensive hardening against the same real, confirmed failure class rather than deferred/speculative work.
