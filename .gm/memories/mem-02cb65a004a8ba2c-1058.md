project/msgpack-usefloat32-lesson: msgpackr's useFloat32 is three lossy settings and one lossless one, and the lossless-sounding option is not lossless. pack.js writes 0xca float32 whenever useFloat32 > 0 and the value is a non-integer in [-2^31, 2^32), then keeps it only if useFloat32 < 4 OR a lossless guard passes -- so 1, 2 and 3 are ALWAYS lossy (3 is DECIMAL_ROUND, the one that reads like a safety net). 4 (DECIMAL_FIT) passes the guard only when value * mult10[exponent] is an integer, computed in double arithmetic, so 8.790000000000001 * 1e6 is exactly 8790000 and it ships float32 and decodes to 8.79: 1 ulp gone on ~5% of short-decimal doubles. Only useFloat32: 0 is bit-exact. Corollary for wire design: put every value that must survive exactly into bytes (a Uint8Array via DataView setFloat64) or into an integer, because typed-array payloads never reach the number encoder at all -- that is why widening the encoder costs nothing on a snapshot whose positions travel as bin records, and costs +4 bytes per field only on raw JS-number floats.
