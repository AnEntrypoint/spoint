project/gpu-lock-run-spawns-node-never-a-shell: on this box `node C:/dev/train/tools/gpulock.mjs run <owner> <command> [args]` spawns the command with shell:false (gpulock.mjs:151), and a bash or sh command path exits 127 -- the ground lane hit exactly that and inferred the lock was not holding anything. It was holding: passing the node binary itself (resolved with `command -v node` in the same shell call) plus a .mjs script works, after which `gpulock.mjs status` reports owner and pid with a live heartbeat (ageSeconds small) and the child's own stdout proves it ran. So the working form is `gpulock run <owner> <node> <script.mjs>`; a shell wrapper is not. A 127 from the wrapper is a spawn failure, never evidence that the lock is unheld, and the way to tell the two apart is status owner+pid, not the exit code of the child. Heartbeat lives in the parent gpulock process for the life of the child, so releasing = the child exiting.
