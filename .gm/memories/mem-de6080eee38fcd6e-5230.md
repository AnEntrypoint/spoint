## Resolved mutable: webgpu-e2e-meshbasicnodematerial-433-dxc-permanent-fail

ROOT CAUSE FOUND via three.js@0.185.1 source (node_modules/three/src/renderers), reconciling with (not contradicting) the earlier mem-c7568d0f1fd78ff1-3104 finding. TRIGGER unchanged: the DXC compile failure itself is a genuine, rare, non-deterministic GPU-driver/DXC race under Dawn's D3D12 backend (re-confirmed: same error signature across 3 independent sessions against varying material/shader shapes, never forced to reproduce on demand). NEW finding is about PERSISTENCE, not trigger: three.js has NO recovery path once a render pipeline fails. Mechanism, three source-cited: (1) common/Pipelines.js:380-406 _getRenderPipeline() caches the RenderObjectPipeline wrapper in this.caches (Map) UNCONDITIONALLY the moment backend.createRenderPipeline() is invoked, before the GPU compile result is known; the ONLY cache-eviction path is _releasePipeline() called from delete()/dispose() on usedTimes reaching 0 -- never on compile failure. (2) webgpu/utils/WebGPUPipelineUtils.js:253-279 (the sync path used by ordinary renderer.render(), promises===null) DOES detect failure via device.pushErrorScope('validation')+device.createRenderPipeline()+device.popErrorScope().then(err=>{ pipelineData.error=true; ... }) -- this IS where 'Render pipeline creation failed (...): DXC compile failed with error: E_FAIL' is logged. (3) webgpu/WebGPUBackend.js:1909 draw(renderObject,info): 'if (pipelineData.error === true) return;' -- three DOES skip re-issuing the broken pipeline in the live per-object draw path once the flag lands. (4) THE GAP: nothing anywhere ever deletes the broken wrapper from Pipelines.caches or resets a renderObject's own data.pipeline, and _needsRenderUpdate() (Pipelines.js:488-494) only re-triggers pipeline creation when data.pipeline===undefined -- which never becomes true again for an object that already got a (broken) pipeline assigned. Net effect: the FIRST time this rare race fires for a given material/shader shape, that shape is permanently wedged for the rest of the process lifetime -- no project code, no user action, and no later successful compile attempt is ever possible, converting a should-be-self-limiting one-frame glitch into the witnessed tick-124-through-8186 permanent magenta-fallback defect on all 91 MeshBasicMaterial instances. This explains why prior short-burst sessions (mem-c7568d0f1fd78ff1-3104, mem-55e56886be73c52d-3150: 5-10 renders each) never observed permanence -- they were too short to both hit the rare trigger AND run long enough afterward to notice nothing ever recovers. FIX: since the underlying compile failure is a real upstream three.js architectural gap (no error-aware cache invalidation/retry anywhere in Pipelines.js/WebGPUPipelineUtils.js/WebGPUBackend.js) and patching three.js's own cache/needsUpdate/render-object-invalidation logic blind carries real regression risk (untestable against three's own WebGPU conformance matrix in this session), implemented a bounded, safe, PROJECT-SIDE defensive mitigation instead of a vendor patch: client/core/SceneSetup.js installStuckPipelineRecovery(renderer, scene), wired in client/app.js right after WebGPU renderer creation. It wraps the PUBLIC, documented renderer.onError hook (confirmed real via common/Renderer.js:606 this.onError=this._onError, invoked from webgpu/WebGPUBackend.js:283-288 device.onuncapturederror), counts occurrences whose message matches /RenderPipeline|CommandBuffer/, and once 3+ fire within a 2s window (debounced with a 5s cooldown to bound cost if the shape is genuinely, deterministically broken rather than a transient race) forces scene.traverse setting material.needsUpdate=true across all materials -- the standard, safe, three.js-supported way to force fresh NodeBuilder/shader-source regeneration, which produces a NEW Pipelines.js cache key and hence a fresh createRenderPipeline attempt, sidestepping the permanently-poisoned cache entry entirely without touching node_modules. LIVE-VERIFIED in the real browser (gm browser verb, real Chromium D3D12/Dawn backend, http://localhost:8099/?webgpu=1&singleplayer&world=tps-game): after page load confirmed renderer.isWebGPURenderer===true, backend.device present, renderer.onError is our wrapped function; synthetically fired 3 renderer.onError({message:'Invalid RenderPipeline...'/'Invalid CommandBuffer...due to a previous error'}) calls matching the exact witnessed error text -- console shows '[renderer] stuck WebGPU pipeline failure detected -- forcing a scene-wide material recompile' firing exactly on the 3rd occurrence as designed, confirming the detection+recovery code path executes correctly against the real production renderer instance with 210 live materials. Could not force the underlying rare DXC race itself to reproduce on demand in this session (consistent with both prior independent sessions' findings that it is not reproducible at will), so the mitigation's real-world hit rate against the actual race cannot be measured this session, but its trigger condition (repeated identical RenderPipeline/CommandBuffer uncaptured errors) is byte-matched to the real witnessed console text from the original 130s play session.
