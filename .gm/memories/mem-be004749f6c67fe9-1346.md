## Resolved mutable: exec-js-windows-detached-child-killed-on-return

Refined root cause via 3 elimination rounds: (1) child_process.spawn detached+unref -> tasklist confirms PID dead within seconds (Windows Job Object propagation). (2) cmd.exe /c start /B wrapper -> also refused, log empty. (3) In-process ESM import()+boot() inside a single exec_js call -> boot succeeded fully (task-output showed complete stdout log incl. '[server] http://localhost:23920 @ 64 TPS' and a 200 status check FROM WITHIN that same task), but a SEPARATE subsequent exec_js dispatch (same daemon, same machine) got ECONNREFUSED against the same port moments later -- proving exec_js dispatches are ephemeral, isolated worker contexts that do not share a live process/listener across dispatches, even a `global.*`-guarded one; the worker (and everything it spawned/hosted in-process) is torn down when its own dispatch task completes, not just when the OS process exits. This means any witness pattern requiring a server that outlives the dispatch that boots it needs the boot AND every probe against it to happen inside ONE exec_js call (or the cdp/browser verb's own process, if that process persists across dispatches and can itself host or reach a long-lived server) -- never split boot-then-later-probe across separate exec_js dispatches on this daemon build.
