Surfaced and fixed a second real bug this exposed: WebGPUUtils.js:127 getTextureSampleData excludes depth textures from isMSAA (isMSAA=false for isDepthTexture===true), so the framebuffer target's real depth texture is created at primarySamples=renderTarget.samples (4x) with NO separate .msaaTexture -- i.e. it is itself a 4x-multisampled depth24plus texture, not a resolve pair like color. vdrs-composite.js's DepthWriteback._pipelineFor cached its pipeline by depthFormat only (default sampleCount 1), causing a live GPUValidationError ('depthStencilFormat: TextureFormat::Depth24Plus, sampleCount: 4' expected vs pipeline's sampleCount:1) on first live test. Fixed by threading sampleCount through DepthWriteback._pipelineFor/render (cache key now depthFormat+sampleCount) and passing depthTarget.sampleCount from the call site; pipeline-cache.js's getPipeline already supported sampleCount generically (cache key + multisample descriptor), just wasn't being used for the depth-only pipeline.
