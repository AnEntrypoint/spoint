Measuring render/startup perf on this repo (scripts/perf-run.mjs, CDP, tps-game singleplayer): four confounds that each produced a wrong number. (1) Bundle churn invalidates a pair: every run logs `[server] serving PREBUILT BUNDLE from dist/client/app.js (built <ts>)` -- if the two runs of an A/B do not print the SAME ts they are not comparable. Another agent rebuilt the bundle mid-pair once and the fix-arm came back looking identical to the base arm (GL draw calls/frame 127 vs 129, shadow 8.6 vs 7.8 ms) while an earlier same-bundle pair showed the real effect (129.3 -> 108.8 draws, 7.781 -> 3.911 ms). Rebuild once, run all arms, record the ts. (2) Under self-inflicted load (cpu>=80, 30-45 chrome processes from sibling agents) CDP Input.dispatchKeyEvent hangs past 25 s; the walk then records zero real input and every frame-time percentile is garbage. Symptom is a run that logs the startup lines and then goes silent for minutes. Discard, never average. (3) The desktop panel is 144 Hz: p50 frame times of 27.7/27.8/13.9 ms are exact divisors (144/4, 144/2) -- vsync, not headroom. Quote draws/frame, GL calls/frame and shadow ms as the load-independent metrics. (4) 'First real movement' is confounded by spawn geometry (player can be wedged against a wall plane at spawn, so the rig cycles W/D/S/A until a direction is unblocked, ~6 s). The rig now also reports nav->inputReachedGame (first inputSequence increment or first wrapped __spoint._drive input); use that to separate input plumbing from a stuck player.
