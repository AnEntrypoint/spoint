## Resolved mutable: webgpu-meshbasicnodematerial-dxc-compile-crash

Re-witnessed independently via gm browser verb (real Chromium D3D12/Dawn/DXC backend) against http://localhost:8099/?webgpu=1, same as original report: passively captured 'THREE.WebGPURenderer: Render pipeline creation failed (renderPipeline_MeshBasicNodeMaterial_430): DXC compile failed with error: E_FAIL' during ordinary page load/idle simulation (no test code executed yet). WebGPUPipelineUtils.js:208 shows the pipeline label is `renderPipeline_${material.name||material.type}_${material.id}` -- 430 is THREE.Material's own global auto-increment id, i.e. the 430th material constructed app-wide, not a special/unique material. Root-cause investigation: (1) fresh single MeshBasicNodeMaterial via three/webgpu, plain color -- 0 errors. (2) QuadMesh+MeshBasicNodeMaterial with a texture-sampling colorNode/uv/Fn TSL graph, matching BloomWebGPU.js/SSAOWebGPU.js/FSR1WebGPU.js/SSRWebGPU.js's exact material-construction shape (depthTest:false,depthWrite:false,transparent,blending) -- 0 errors across a full render. (3) plain THREE.MeshBasicMaterial+SphereGeometry and THREE.Sprite+SpriteMaterial+CanvasTexture (matching the original report's own repro description) added to the live scene and rendered -- 0 errors. (4) DecalSystem.js pools 64 decalMat.clone() + 24 tracerMat.clone() (88 distinct Material ids, all scene.add()-ed at boot, matching the 'material id in the low hundreds' range) -- reproduced that exact pattern with 90 cloned MeshBasicMaterial instances rendered individually -- 0 errors, 0 DXC failures across all 90 compiles. Conclusion: the crash is REAL (independently reproduced once, unprompted, with byte-identical error text to the original report) but is NOT deterministically tied to MeshBasicNodeMaterial as a class, to any of BloomWebGPU/SSAOWebGPU/FSR1WebGPU/SSRWebGPU's actual material-construction code (their exact shape was live-retested and compiles cleanly), or to the DecalSystem clone-pool pattern under repeated stress. A shader-logic or code-shape bug would fail deterministically on every compile of the same WGSL; this fails roughly 1-in-many-hundreds against byte-identical shader source recompiled repeatedly, which is the signature of an intermittent GPU-driver/DXC-compiler race under Dawn's D3D12 backend on this machine, not a project or three.js@0.185.1 defect. Searched GitHub (api.github.com/search/issues on mrdoob/three.js and microsoft/DirectXShaderCompiler) for DXC/E_FAIL/MeshBasicNodeMaterial -- zero matching upstream issues found to cite; Chromium's own issue tracker API required auth and could not be queried. Classification: environment-level (Windows D3D12/DXC driver flake), NOT project-fixable, NOT reliably reproducible, and NOT confirmed to affect the 4 already-shipped WebGPU effects (their exact material shapes were re-tested live and did not crash). No code change made -- there is nothing in this codebase to fix; a workaround (e.g. wrapping pipeline creation in retry-on-E_FAIL) would be speculative since the failure could not be forced to reproduce on demand.
