Editing a THREE.ShaderChunk + material.needsUpdate is a silent no-op: the program cache key hashes shaderID/defines, not resolved chunk text. In three r185 needsUpdate also does NOT rebuild a node material whose cache key is unchanged, so a JS build-time branch can freeze wrong forever -- terrain-lighting-tsl instead builds the sun term for every DirectionalLight except ShadowPipeline cascades and multiplies by a per-light uniform(0).onRenderUpdate(light === sunRef.light) flag. An early return from InstancedMesh2's onBeforeShadow leaves unpatchMaterial UNPAIRED: it restores customProgramCacheKey from a null base, so WebGLPrograms.getParameters throws TypeError, the scene-color node aborts and RETURNS, and every remaining node of that frame is skipped for the rest of the session. It fools measurement: frame time and CPU drop sharply and draw calls/frame collapse (162 -> 5) because the scene is no longer drawn. Always call the base hook; witness draw calls, not frame time. VegImpostorTier.createSharedImpostorMesh must stamp a +-1 boundingBox (not only a radius-1 sphere) on its zero-area near-LOD geo: @three.ez computeBVH builds leaves from geometry.boundingBox, so a zero-volume box silently culls 100% of instances (count stays 0, no error). VegetationBuild.simplifyGeo/capGeo must always return a NEW geometry with instanceIndex stripped: addLevel reuses the LOD object when geometry===existing (two levels alias one instanceIndex array, so trees vanish at a cutover) and patchGeometry's stamp survives clone(), so addLOD re-clones+warns every build (~4 MB/frame GC churn). A THREE.BatchedMesh given an array material silently never draws: projectObject iterates geometry.groups for array materials and BatchedMesh groups stay empty (0 draw calls, no error); material-bucket-batcher.js _bucketFor unwraps seedMaterial[0] and every BatchedMesh consumer must. Model pool: never bind one shared BufferGeometry to N meshes -- wrap in a fresh shell sharing attributes/index (sharing gives re-clone+warn churn and VAO cache collision, keyed geometry.id, objectId 0 => GL_INVALID_OPERATION). ClusterLodMesh._render fires once PER GROUP per frame and renderList entries hold refs to pooled group objects, so re-running cull/LOD mid-frame rewrites start/count of already-queued draws; keep the _lastRenderFrame===frame early-return and never issue raw gl draws there (VAO not yet bound => ANGLE 'insufficient buffer size').
