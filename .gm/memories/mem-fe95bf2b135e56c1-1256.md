project/netcode-remote-interp-delay-is-jitter-driven-2026-10-02: SnapshotTimeline.targetDelayMs = clamp(tickMs, 400, 1.5*intervalMs + jitterMs) is a function of measured jitter, not a constant -- measured over WebSocket the jitter estimate (p80 minus min of 90 arrival offsets) runs 16 / 25 / 59 / 187 ms at 0 / 50 / 100 / 150 ms added latency and the fitted render lag behind server truth follows at 36 / 98 / 190 / 408 ms. The harness's `remote in->visual p50` (~78-95 ms at RTT ~20) is an ONSET metric: it includes the ~31 ms the mover needs to cover the 0.25 m MOVE_ONSET_M detection threshold at 8 m/s plus ~17 ms of up-path and tick quantisation, so `remote eff. delay ms` is the latency-only figure and `remote - server ms` is the part added after the server already moved. Two smaller-buffer variants were measured and rejected: DELAY_INTERVALS 1.5 -> 1.0 buys 6 ms clean / 20 ms at 150/25/5 but produces held frames (buffer dry past MAX_EXTRAPOLATE_MS=100) on 1% of clean-link frames where there were none; base offset from p10 instead of the window minimum is 1-2 cm worse at every condition. Re-measure with the new harness columns (interp jitter ms, interp interval ms, remote - server ms, extrap/held %) before touching SnapshotTimeline again.
