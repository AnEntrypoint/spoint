Over plain WebSocket the snapshot stream rides TCP, so every lost segment head-of-line blocks every later snapshot for a full retransmit (net-conditioner retransmitPenalty = max(20, 2*latency+jitter) = 325 ms at 150/25). Measured in scripts/netcode-conditioner-harness.mjs at 150/25/5: ws gives remote in->visual 899-921 ms, remote eff. delay 454 ms, remote err vs present 170 cm, input starves 18.4/s and 21% starved samples; the datagram channel (--channel=udp, per-datagram drops) gives 434 ms, 212 ms, 86 cm, 0.2/s and 5%. No interpolation tuning recovers the ordered-stream number -- it is the honest minimum for TCP at that loss rate. Snapshots are already flagged SNAP_UNRELIABLE and reach the client as true datagrams over WebTransport (WebTransportClientTransport.sendUnreliable -> session.datagrams) and wireweave; WebSocketTransport.sendUnreliable has no datagram backing. build/Release/webtransport.node is not built in this checkout and Node has no WebTransport client, so the datagram path cannot be witnessed locally: host with WebTransport to get it.
