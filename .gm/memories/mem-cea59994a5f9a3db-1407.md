client/app.js _finishLoading adopts the running scenery build for one more SCENERY_BUILD_TIMEOUT_MS window whenever _sceneryBuildPromise is still set at the cap, not only when window.__terrain is absent. The old condition tested window.__terrain, so a cap fire after the planet had landed skipped the adoption entirely and fell through to _resolveWorldBuilt(), revealing a world whose vegetation did not exist yet - the same class as the AMD settle:false / world objects missing failure. The wait stays bounded at two windows and still never starts a second build, because _buildWorldScenery returns the in-flight promise.

Vegetation creation never resolves on the SwiftShader witness path: boot:vegetation-created did not fire in the uncontended 44 s baseline, not 300 s into a contended run, and not in either fix run. Rocks and grass settle within about 75 ms of boot:foliage-started, so the stall is specific to vegetation, not to the foliage phase. Consequence: no scenery gate on the software renderer can be satisfied by the build; it always falls back to the duration cap.

Measured cold-build spread for SCENERY_BUILD_TIMEOUT_MS = 30000: AMD rdna-2 legacy WebGL2 settles _buildWorldScenery at window+30.02 s so the cap fires on essentially every real load; SwiftShader returns the backdrop at 28.489 s and had not finished by 44.039 s; under six-lane contention the same backdrop reached 71.414 s.
