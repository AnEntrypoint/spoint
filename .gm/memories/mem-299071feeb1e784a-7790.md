project/planet-wide-multiplayer-architecture-2026-10-05: DECISION: planet-wide multiplayer = dynamic PROXIMITY CLUSTERS, one existing server world per cluster, each cluster its own flat chart (the ChartReanchorService follows the cluster centroid), clusters hosted in worker processes (several small worlds per process, never one process per player), a pure deterministic assignment function (src/shared/clusterAssignment.js, landed default-off and unwired) deciding membership with stay/join hysteresis; one-cluster is today's world unchanged, matches stay rooms/instances (bin/room-orchestrator-boot.js). Rejected with numbers: (A) one world one chart: shared-chart slope under EACH of two players (flat sea, relief 0, midpoint anchor) 2 km apart 0.90 deg, 5 km 2.25, 20 km 9.05, 50 km 23.15, 100 km 51.83 (>45 deg limit, unwalkable); per-cluster charts at the lattice cell anchor 0.28-1.58 deg at every gap (bound = cell worst angle 2.26 deg = 2508 m at R 63600, 32 anchors/face); beyond 63.6 km the old solver returned the constant -63600 and a flat collider was built (witnessed at 64 and 100 km), now ChartRangeError + named warning + no collider; antipodal players made chartAnchorDecision THROW every tick, now a named refusal players-straddle-the-planet, and a party whose worst player is >= 45 deg from the anchor is refused with party-spread-exceeds-walkable-chart. (C) world per player: Jolt wasm heap is FIXED at 128 MB (HEAP8.length never grows): ~21 MB per default PhysicsWorld, so 6 worlds per wasm module (10 with joltLimits maxBodies 2048), the 7th/11th PhysicsWorld.init aborts 'Aborted(OOM)'; full tps worlds with terrain: 6 ok, 8 abort; a one-world process is 81-84 MB RSS (bare node 38) and ~1.3 s to create (heightfield refine), so 256 players = 256 processes (~21 GB) is unviable, while the 256-player random spread over 120 km needs 160 clusters (not 256) and clusters per process are heap-bound. (D) true sphere/per-body gravity: Jolt build is single precision (a body at 63.6 km reads back with 1.5 mm error and 7.8 mm quantisation, 1/128 m above 32 km); CharacterVirtual SetUp/GetUp and an Update gravity argument exist but BodyInterface/MotionProperties/BodyCreationSettings SetGravityFactor is a SCALAR (no direction), so every dynamic body would need AddForce each step; it rewrites every y-up assumption (rejected again; the precondition to revisit is a double-precision Jolt build). Load is NOT the reason to partition: physics step 0.025 ms/world (2 players), 0.165 ms at 16 players, 0.37 ms p50 at 64 players in ONE world. The reason is chart validity; the load that DOES scale with spread is terrain upkeep: ~28 ms CPU per second per walking player (7 m/s, linear in separated players: 8 spread players = 22.5% of a core, 36 saturate one), and ground coverage latency: HeightfieldStreamer builds ONE field per pass (about 4.5 s wall each on Windows, 2 ms slices + ~15 ms timer yield) and caps at 8 fields / 8 collider centers, so 16 players 1 km apart had 7 with ground after 20 s, 14 after 60 s, and 64 players never exceeded 9 (tphys.maxFields and vegetation.colliderMaxCenters passthroughs added, default unchanged). INTERACTION RULE: relevanceRadius is 200 m (tps preset; ring of 3x3 cells), so two players farther apart than the cluster link distance (default 1000 m = max(ring extent, weapon range, lag-comp reach)) cannot see or hit each other and may live in different worlds; a hit/event is only ever resolved inside one cluster, global state (chat, scoreboard, match phase) travels over a router bus (RegionRouter EVENT_REPLICATE is the precedent). CLUSTER ASSIGNMENT (measured, scratchpad/planet-arch/pW_cluster.out): member-to-centroid radius <= 1.25 x 2508 m to stay, <= 0.8 x 2508 m to join or merge, link 1000 m, hysteretic single-linkage + eviction + seeded packing + converged merge, ids from a monotone counter, ties by player id, inputs sorted by id so 200/200 shuffles are identical; ramp together->apart->together with wobble 0..30% of the split diameter gives exactly 2 flips (2 handoffs) against 2..142 flips for a single threshold; antipodal pair = 2 clusters, no throw; zero-length, NaN, null and duplicate ids are returned in rejected[] by name; a 100-player chain over 50 km at 500 m spacing = 11 clusters, max radius 2001 m, worst member 2.91 deg from its lattice anchor; 40 players random-walking 8 km for 10 min = 24 handoffs, 11 merges, worst 4.38 deg (analytic bound 3135 m + 2.26 deg = 5.08 deg); cost 0.16 ms at 16 players, 0.67 at 64, 3.4 at 256, 8.9 at 1024 (O(n^2), run it at 2-4 Hz, not per tick). WHAT BREAKS: a CONTIGUOUS crowd wider than ~2 stay radii (about 6 km) has no seamless partition, so a continuous play area is bounded by one chart (map design rule), and a fight across a split line is not supported. SCENARIOS (analysis unless marked): authoritative shooter = the cluster model; rollback and lockstep peer profiles pin one chart (ctx.peerSession already gates the re-anchor) and must assert at room creation that the map extent fits the chart (loud, named); P2P rooms and host-in-browser are single-cluster, a joiner farther than the cluster radius is refused with a named reason; singleplayer worker is one cluster; editor ops carry base-chart positions (canonicalTransfer) and route to the cluster covering the entity; spectators join the target's cluster and follow its handoffs; replays record per cluster (epoch field needed, row chart-reanchor-transform-ring-replay-region-epoch); rejoin uses the base-chart position persisted at disconnect and the pure assignment function. WIRE: each cluster world keeps its own chartEpochLedger; a handoff is a hard resync (new world endpoint + session token + chart snapshot, epoch ledger reset, existing 'resync:true' path), so CHART_REANCHOR itself needs no cluster id; the router-side id is the cluster counter. COORDINATES: a chart is a rigid frame of one Euclidean planet-centred space, so base-chart positions stay exactly invertible at planet scale in f64 (1e-11 m round trip) even where the base chart has no ground. EXISTING PRECEDENT AND ITS GAPS: src/sharding/RegionRouter+RegionWorkerEntry is a flat 512 m grid, router proxies every frame as base64 IPC, handoff carries only position/rotation/velocity/health with no chart, epoch, prediction or entity state, so cluster hosting generalises it but does not reuse its handoff. ENTITY PARTITION IS THE LARGE UNSOLVED PIECE: every cluster world today would instantiate the full entity set (statics replicate per cluster, 22 us per static per flip with tiles, 7-8 us without); entities need a home location and cluster worlds load only entities within coverage (others dormant). WHAT WOULD CHANGE THE RECOMMENDATION: (1) a required interaction range above the link distance (long-range vehicles, 3 km sniping) -> seams or larger links; (2) a double-precision Jolt build -> D (one planet-centred world); (3) in-process multi-world measured cheaper than one heap per process (apps/ctx per world) -> in-process hosting; (4) entity partition costing more than the arena restriction -> ship only 'rooms plus one chart' and refuse far joiners; (5) measured two-browser interaction across a split at the stay boundary showing visible popping.
