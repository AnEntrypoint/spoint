A collider rebuild that comes back deferred leaves more bodies live than the body cap, because the cap bounds one pass rather than the resident set. Measured at 16 players on tps-game (radius 64, baseCap 384, centreScale 2, effectiveCap 768) by running the initial ring as repeated budgeted passes: 983 live trunk colliders against a cap of 768, 28% over, and a different body set from the single unbudgeted pass (position hash 8c5b065d vs 77096680). classifyRings limits desired to effectiveCap per pass with a per-cluster quota of cap/centres, and both reset every pass, while live keeps what earlier passes added; afterwards the only removals are the keep set (everything stayed inside keepRadius) and evictOverBudget, which fires on resident bytes alone (263444 of 3145728 B here, so it never ran). Any deferred rebuild reaches this state - _rebuildMulti returns _deferred when MAX_NEW_CHUNKS_PER_PASS (64) or COMPUTE_BUDGET_MS (2.5) bites, then curCenters is not updated and removals are skipped - so it is reachable in steady state whenever more than 64 ring chunks are new, not only at boot.
