spoint lockstep sim rate: the ceiling is peer count and link tail, not a tunable. Measured with scripts/peer-profile-harness.mjs --world=lockstep-rts, 20 s arms, inputDelayTicks=6, startSkewMs=400, cond 75/10/5: 2 peers 28.8-29.4 Hz, 3 peers 28.6-28.8, 4 peers 26.6-27.0 -- all zero desyncs, zero drops. Two thresholds were tested and neither recovers it: maxCatchUpTicks 4/8/16/32 gives 27.05/27.40/27.20/27.13 (flat, and stalls GROW 1341->1520 as it rises), and inputDelayTicks 6/10/14/18 collapses stalls 1358->345->93->21 but only converts them into timeSyncYields 72->94->123->130, holding 27.2-27.8. Cause: ready(t) in src/netcode/LockstepGameLoop.js needs every peer's input for t, so the slowest peer paces the sim, and linkDelay adds 2*LAT+JIT on a loss event so the tail exceeds the delay budget more often as N grows. Do not tune these; treat sub-target rate as the cost of the link and roster size. Separately: the 12-tick startup maxStallRun seen on peer-a only is the harness default --startSkewMs=400, not a defect -- start() pre-confirms only LOCAL ticks 1..inputDelayTicks, so tick 1 cannot run until the second peer exists; at skew 0 maxStallRun is 1 on both and simHz is 30.0 at 25/5/1. Refutes the earlier 24.2 Hz claim, which does not reproduce at any condition tried (worst reproducible 27.2).
