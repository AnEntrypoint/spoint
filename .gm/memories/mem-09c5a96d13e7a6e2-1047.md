Making an async build joinable (a second request returns the in-flight promise instead of starting a new one) silently breaks any caller that resets shared state before calling it. In client/app.js the retry-toast onClick did `terrainBackdrop.dispose(); terrainBackdrop = null; _buildWorldScenery()`. Once _buildWorldScenery returned the in-flight promise, that click disposed the backdrop the running build was populating, started nothing new, and then toasted success -- the join cannot honour a caller reset-intent because the in-flight build is already committed to the old object. Any joinable slot needs its callers to check the slot first and skip the reset, or the slot needs to expose a separate restart that genuinely cancels. General rule: when you add a join, audit every call site for state it mutates immediately before calling. Found by adversarial review, not by the implementer, and not caught by the happy-path witness -- the witness only proves the boot path ran, not that every caller of the changed function still makes sense.
