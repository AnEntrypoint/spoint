fireKernel delta (journal) snapshots: undoing a chain of deltas leaves the kernel pending queue set to the pending list of the OLDEST undone delta (the boundary just after the target), not the target boundary s. fireTimeline.restoreEntry then re-queues log events whose tick is greater than entry.prev and whose id is not already in that queue -- so every event consumed between the target boundary and the next boundary is in the log but looks already queued, and is silently dropped. Symptom: a peer that rewinds while an ignition sits in a pending-at-boundary queue replays without it and ends with zero fire (active 0, checksum 0) while its peer keeps burning; intermittent because it needs a rewind in the window between consuming and re-snapshotting. Fix: kernel.markRestored(pending) after the undo chain, which sets pending to the target boundary s captured list, clears the open-step flag and re-baselines preStep (preStep is otherwise stale after any delta rewind, so the next takeDelta captures the wrong boundary scalars). Full snapshots hid this because kernel.restore(snap) restores snap.pending wholesale. Witness: scripts/fire-peer-rollback-witness.mjs 8 rollback + 8 lockstep arms at 0 mismatches after the fix; 4 of 7 arms mismatched before.
