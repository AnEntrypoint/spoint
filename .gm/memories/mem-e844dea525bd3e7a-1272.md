The 30 s SCENERY_BUILD_TIMEOUT_MS window is charged for the WHOLE of _buildWorldScenery, but the post-race decision only tests window.__terrain, i.e. the planet. Measured: on AMD rdna-2 legacy WebGL2 the planet is initialised at window+17.23 s (boot:backdrop:planet-initialised 31362 against boot:backdrop:start 14131) while the full build resolves at window+30.02 s -- within 20 ms of the cap. On headless SwiftShader the same tail is even longer: createTerrainBackdrop returns at 28.489 s and boot:scenery-built fires at 44.039 s, 15.55 s later. The named cost in that tail is PLAYABLE_BUDGET_MS = 4000 (the vegetation/rocks/grass prewarm, three in parallel), plus `await Promise.all([rp, gp, vp])` foliage creation and warmSceneryShaders. So on a cold load the timer wins essentially every time and the run only survives because window.__terrain was already set ~12.8 s earlier. Gating the wait on the planet instead of on the whole build would buy back that margin without moving the reveal, because _revealWorld already awaits _worldBuiltPromise which the build resolves at its end. Also note: setTimeout callbacks on this path get starved by the busy main thread -- in several witness runs the cap timer fired seconds late and the build promise won the race instead.
