Deep-detail tier for AGENTS.md "Measurement and witnessing". AGENTS.md keeps the rule, the threshold and the script name; this memo keeps the numbers, the scenario and the derivation. Read this before trusting any harness number.

GPU arms and adapters
- Witnesses can launch Chromium on SwiftShader silently, so historical timing gates were software numbers. `gpu-probe.mjs assertGpu` after navigation asserts the REQUESTED adapter.
- AMD LUID is per-boot: 62340 on 2026-10-07, 71831 in an older note. `adapterLuidFor('amd')` reads the DirectX registry each run; `perf-run` exits 2 when `--gpu=amd` finds no AMD entry; `--use-adapter-luid=0,<luid>` with a value Chrome cannot resolve silently runs the DEFAULT adapter, which is AMD on this box as of 2026-10-07 afternoon.
- AMD iGPU (Radeon(TM) Graphics): the tps-game page loses its GPU context during boot, after which Chrome refuses every later context on that page — `canvas.getContext('webgl2')` fails with creationError "Web page caused context loss and was blocked", `navigator.gpu.requestAdapter()` returns null, `page.evaluate` stops answering (about:blank still probes AMD: "ANGLE (AMD ... D3D11)"). Same on WebGPU and `?legacygl=1`; `--disable-gpu-watchdog` does not help and `SPOINT_UNLOCK_RAF=0` wedges identically, so the vsync flags are not the cause. `info.render.calls` advances a few draws first, so it is a boot-time GPU submission or sync readback past the Windows TDR window on the integrated adapter (legacy GL: "[minimap] baked ... in 60909ms"). 2026-10-07: 3 of 6 AMD gate runs died mid-boot, 2 more captured 0 draws. NVIDIA never did. Race every `page.evaluate` against a timeout (`evaluateOrThrow`, `perf-run`'s cdp-timeout) or the run hangs.
- Adapter inventory 2026-10-07 (`reg query HKLM\SOFTWARE\Microsoft\DirectX /s`, now surfaced with vendorId/deviceId/lastSeen by `directxAdapters()`): NVIDIA GeForce RTX 3060 Laptop GPU LUID 1503521746 (VendorId 0x10de, DeviceId 0x2520), the SAME device again at LUID 80375, Microsoft Basic Render Driver 80230, AMD Radeon(TM) Graphics 62340 (VendorId 0x1002, DeviceId 0x1681). The two NVIDIA entries share VendorId, DeviceId and DriverVersion and differ only in AdapterType (0x342 vs 0x2313); LastSeen is identical, so no registry field discriminates them. There is no Intel adapter, so `--gpu=intel`/`--gpu=igpu` can only fail loudly (exit 2, naming the inventory and `--intel-adapter-luid=`).
- `verifyVendorLuid(vendor, luids)` settles which LUID is live by launching: `node scripts/lib/gpu-probe.mjs --verify-luid=nvidia --luids=1,1503521746,80375` gives 1503521746 and 80375 -> `ANGLE (NVIDIA, NVIDIA GeForce RTX 3060 Laptop GPU (0x00002520) Direct3D11 vs_5_0 ps_5_0, D3D11)` vendorMatches true, and luid 1 -> `ANGLE (AMD, AMD Radeon(TM) Graphics (0x00001681) Direct3D11 vs_5_0 ps_5_0, D3D11)` with rasterizer "accelerated" and vendorMatches false. So the duplicate NVIDIA entry is harmless (both drive the 3060) and first-match was never wrong for nvidia; the live class is an UNRESOLVABLE LUID, which Chrome ignores while still reporting an accelerated session. `requireAccelerated` therefore cannot catch a mis-selected vendor — every vendor arm must assert the renderer string (`assertGpu(page,{expectVendor})` / `witnessGpu`).
- The unpinned default adapter is not stable within a day: `node scripts/lib/gpu-probe.mjs --accelerated` (no LUID) got AMD Radeon in the afternoon, but the committed `.frame-time-baseline.nvidia.json` was captured by an unpinned arm at 09:54 (`fceb0e8a`) and its `gpu` field — written from `assertGpu`'s probed `haystack`, not from the flag — reads `ANGLE (NVIDIA, NVIDIA GeForce RTX 3060 Laptop GPU ...)`. That baseline escaped the mis-selection by luck and stays comparable to pinned runs only because `95bdfe16` pins every vendor arm.

Frame-time gate
- A vsync-locked p50 is a refresh divisor, not work: 144/1 = 6.94 ms static, 60/1 = 16.67 orbit, on ONE page. `frame-time-gate.mjs` unlocks rAF with `--disable-frame-rate-limit --disable-gpu-vsync` (`SPOINT_UNLOCK_RAF=0` is a debug override).
- Baselines are PER-VENDOR: `.frame-time-baseline.<vendor>.json` chosen by `--expect-vendor=`/`SPOINT_GPU`; `frame-time-baseline.mjs` refuses one captured on a different adapter. NVIDIA 2026-10-07: static p50 10.80 ms, orbit p50 11.33 ms, 4679 veg instances, ~278000-285000 triangles/frame. AMD has none, so the gate fails loudly; the stale `.frame-time-baseline.amd.json` is an empty-view run (static 18.25 ms / 273143 tri, orbit 2.70 ms / 8146 tri).
- Orbit arm is a bounded +-0.25 rad sine sweep that must render >= 50% of the static arm's triangles; a full 360 deg spin measured an empty view.
- A reached-triangles arm is exempted only when the backend reports isWebGPU, requiring draw calls, frames and `window.__vegProfile.totalInstances` instead. Its camera is posed off the live player (player + 50,10,+50) at `?at=-15,-12.5`, or it frames empty ground. `perf-run` reads `window.__veg.profile.totalInstances` OR `window.__vegProfile.totalInstances`.

Counters that lie (why perf rows are decided on counted work units)
- `_lastCollisionMs` moved 0.310 -> 0.423 (+37%) between two arms of one build while work-unit counters moved under 1%.
- A wall-clock ms/s gate on a shared box measures the box: the same ring-scale arm read 147.78 and 73.55 ms/s with every work counter identical.
- A counter the code never increments is a silent pass: `physics.getBodyCount` and `collectMs`/`collectCount` did not exist, so two gates compared `null` and passed.
- Authoritative draw count: `perf-run.mjs drawsInstrument.authoritativeField` (`wgpuDrawsPerFrame`/`glDrawCallsPerFrame`) = 141, the per-frame DELTA of `info.render.drawCalls` since `8f5214d164`.
- three 0.185.1 WebGPU `Info`: `info.render.calls` is CUMULATIVE and the only reliable liveness signal; `info.render.drawCalls`/`.triangles` read 0 there and there is no `info.render.frame`. Per-frame numbers come from the fields `Info.reset()` zeroes.

Input and walking
- CDP `Input.dispatchKeyEvent` DOES reach the app's input bucket (witnessed 2026-10-07, NVIDIA accelerated, `?multiplayer&world=e2e-ci-arena`, real `boot()` server): KeyW held 10.17 s -> accumulated 65.390 m (net 65.335, mesh 65.486), 754 -> 1344 input steps, `window.__app.sentInput={"forward":true,...}`; KeyS/A/D each 33.9-34.9 m over 5 s with the matching flag. The old "60 s of KeyW moved 0.9 m" was NOT an input failure: tps-game's player does not move at all (server prints `[physics] peak bodies 146/10240, peak active 0, contact manifolds 0/10240`, z frozen at -10.140115737915039 for the whole hold, `vel` [.., 0, 7]) and it stalls identically in `?multiplayer`, so it is not the singleplayer worker either.
- `perf-run.mjs`'s `inputReachedGame` is structurally always null, so its "synthetic keys never reached the app input bucket" diagnosis is false: line 542 needs `s.seq != null` but `getLocalState().inputSequence` is `undefined` on every sample (it is server-authored; `inputSequence` has 0 matches under `client/`), and line 543 needs `!seq0.input` but the `_drive` wrap at 504-507 writes `window.__rigLastInput` on every step including idle, so `seq0.input` is always truthy.
- Read input acceptance from `window.__app.sentInput` / `sentInputCount` (shipped, post-mask payload actually handed to `client.sendInput`), not from `nav->inputAccepted`. Keys need no pointer lock (that is mouse look only, `app.js:2224/2226`); `freezeLocalInput` is never called; CDP sends `code` correctly and the event is trusted, unprevented, on BODY, with focus and visibility true.
- A walk witness measures accumulated path length (sum of sampled position deltas), never net displacement: a walker that reaches its waypoints then stalls on arena geometry reads 18.47 m net for a 150 m walk.
- `window.__spoint._drive` is `Relocation.js drive()`, called by `app.js` each input step; wrapping it is the sanctioned way to OBSERVE input. `?multiplayer`: 767 input steps in 11.6 s, 15.0 ms input period.

Harness rules and traps
- `npm run check` (2026-10-07 order): gpu-free witness arm (~30 s, 9 witnesses) -> `fire-witness-gate.mjs` -> `check-frame-time-baselines` -> the opt-in `SPOINT_GPU_WITNESS` veg arm. A witness must exit 0 AND print `RESULT: PASS`, capped at 600 s so a hang fails CI. `npm test` ends in the fire gate alone. `check.mjs` parses only tracked files under `src,client,apps,scripts,bin`.
- `?singleplayer` sees `players:0` and acks `ok:false`, so a witness needing the server to act on a client message passes `--params=multiplayer`. `net::ERR_ABORTED` is a cancellation; only a real failure or HTTP >= 400 fails an arm. A harness returning an uncompared `{expected, got}` passes either way: one `expect()` per measurement plus non-zero exit.
- TSL-vs-legacy parity criterion (written BEFORE any frame): a region matches iff cross-renderer meanAbs/channel <= 3 x max(same-renderer noise floor, `QUANT_FLOOR` 1.0); floors differing >3x = INDETERMINATE.
- gm `exec_js` dispatches are ephemeral, isolated worker contexts: a server booted in one is gone by the next (ECONNREFUSED); detached+unref spawn dies too (Windows Job Object). Screenshot trap: `TerrainBackdrop.renderPlanet` rebuilds eye/target from `camera.getWorldDirection()`, broken for a manually posed camera (pure sky). Pre-change control for a converted witness that fails: gm `git_show {path, rev:"HEAD"}`, write to `scripts/.<name>.mjs` so `./lib/...` resolves, run, delete; a failure identical at HEAD is environmental.
- gpulock: `gpulock.mjs run <owner> bash ...` exits 127 — pass the node binary + a `.mjs` script. It returns 0 even when the witness failed, so grep the run's own log for `RESULT:`. `gpulock status` `held:false, stale:true` = lock free, stale holder never resumed.
- Environment: `localhost` resolves ~200 ms vs `127.0.0.1` 5 ms — use the literal IP. Snapshot bundles with `cp -p`, never `cp`; two harness reports are comparable only on the same code, so check mtimes of every source file a report depends on.
- Unshipped measured win: `Weather.js _respawnDroplet/_respawnFlake` re-sampled `frame.groundHeightLocal` at a new random position on every recycle (~26k calls/s = 65% of all sampling).

Which witnesses belong in the gpu-free arm (measured 2026-10-07)
- Admission is by capability, not by cost: a witness is gpu-free iff it needs no browser and no GPU context. `check.mjs` refuses browser/GPU witnesses BY NAME (prediction-drift included), so adding one to that arm fails loudly instead of launching Chromium on SwiftShader and reporting a software number.
- `terrain-residency-seam-witness` is the shape to watch for: it asserts nothing, so it passes whatever the code does. Admission is not validation -- a witness with no `expect()` is a silent pass (same class as the never-incremented counter).
- `collider-ring-scale-witness` costs 85 s and was red on 2026-10-07; it is a wall-clock ms/s gate on a shared box, so its failures need the work-unit check before they are believed (147.78 vs 73.55 ms/s with identical counters).
- `fire-tile-reclaim-witness` can turn `npm run check` red for box contention alone.
- `fire-tps-game-witness.mjs` is a fire witness that `fire-witness-gate.mjs` does NOT list, so the fire gate never runs it.
- `edge-collider-draco-witness.mjs` rewrites tracked `apps/tps-game/*.glb` in place -- never run it inside a gate, it dirties the tree it is supposed to be checking.
