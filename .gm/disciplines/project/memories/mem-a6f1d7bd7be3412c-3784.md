Debugging playbook for live GL-error/rendering-defect root-causing, proven on two real bugs in one session (terrain/water sampler-collision + TEXTURE1 dirty-cache desync; tree flicker polygon-offset-insufficient). Steps: (1) browser-verb DOM-eval UV_HANDLE_CLOSING crash workaround = route all real window/document access through page.evaluate() inside a capture-prefixed script, never bare window/document identifiers in the outer vm-context script body; page.click()/keyboard/mouse (real Playwright input) needed for pointer-lock, synthetic dom=selector click does not count as a trusted gesture. (2) Read the browser's OWN console text via a cache-disabled hard reload (Network.setCacheDisabled + page.reload) -- multiple distinct GL bugs share the same gl.getError() code (GL_INVALID_OPERATION=1282 covers feedback-loop, sampler-type-mismatch, AND insufficient-buffer-size, all different bugs) but the driver's own console string disambiguates them. (3) Monkeypatch drawElementsInstanced/drawElements via page.addInitScript (installs from frame 1) to drain-then-check gl.getError() around the real call and capture new Error().stack on failure -- pinpoints exact file:line origin. (4) Query LIVE GL state (gl.getParameter(TEXTURE_BINDING_2D), gl.getTexParameter(...COMPARE_MODE), getFramebufferAttachmentParameter object-identity checks) rather than trusting JS-side dirty-cache variables -- a cache variable can say 'already bound correctly' while THREE's own renderer.render() pass (running between two of the target system's own draw calls in the same frame) has silently rebound the same texture unit; this makes ANY JS-side skip-the-rebind-if-cached optimization on a shared texture unit unsound whenever a third-party renderer can also touch it. (5) For flicker/temporal defects: gl.readPixels a known-stable non-edge non-wind-animated screen coordinate across N requestAnimationFrame ticks, compute a flicker score (frame-to-frame color delta count above a noise threshold), then toggle candidate systems off one at a time (occlusion queries, a RenderGraph node via window.__renderGraph.disable(id), an update function via monkeypatch-to-noop) and re-measure until the score hits zero -- this proves the cause empirically instead of arguing from source, and caught that three prior sessions' occlusion-hysteresis fixes for a tree-flicker bug were targeting a completely inert mechanism (occlusion queried=0 candidates the whole time). (6) Locate the exact target object via scene.traverse(name) or InstancedMesh2.getPositionAt(i) projected through camera.projectionMatrix.clone().multiply(matrixWorldInverse) -- do not assume from a screenshot which system owns a given pixel; this session's first flicker investigation wasted a pass on env-sillos (a placed GLB structure) before finding it was actually testing the wrong object entirely, not a Vegetation.js tree. (7) A/B the actual fix VALUE live (e.g. material.polygonOffsetUnits = X; material.needsUpdate = true) at 2-3 candidates using the same harness BEFORE editing source -- turns 'raise it and hope' into a decisive proven number. Verify the shipped fix with a genuinely fresh session + hard reload reading straight from the served bundle (no live-patch), confirming the file change actually reached the running page. (8) app.clientMachine.send('TOGGLE_EDITOR') (not cam.setEditMode directly) + cam.setEditCameraPosition/yaw/pitch for reproducible screenshot poses -- but yaw/pitch writes can silently no-op if cam.getMode() is still 'tps' not 'edit', or if a docked editor panel is stealing pointer-lock focus; check getMode() first if a positioning attempt doesn't visibly change the screenshot. Full narrative + all commit shas in AGENTS.md's new 'Debugging playbook' section and its 2026-07-10 audit-log entry.
